## 1교시형 문제 풀이

## 1. 대체 불가능 토큰 (NFT; Non-Fungible Token)

* <b>I. 개념:</b> 블록체인 기술을 이용하여 디지털 자산(이미지, 영상, 오디오 등)의 소유권을 증명하는, 고유한 식별값을 가진 상호 대체 불가능한 가상 토큰.  
* <b>II. 주요 특징:</b>  
* <b>고유성(Uniqueness):</b> 토큰마다 고유 값을 가져 1:1 교환이 불가능.  
* <b>소유권 증명 & 추적성:</b> 블록체인 분산 원장을 통해 위변조가 불가능하며 소유권 이력이 투명하게 공개됨.  
* <b>스마트 컨트랙트:</b> 저작권자에게 지속적인 로열티 지급 등의 조건 프로그래밍 가능.

* <b>III. 활용 분야:</b> 디지털 아트, 메타버스 자산, P2E 게임 아이템, 실물 자산 토큰화(RWA).

## 2. 모델옵스 (ModelOps)

* <b>I. 개념:</b> AI 및 머신러닝 모델의 개발, 배포, 모니터링, 재학습 등 전체 라이프사이클을 자동화하고 엔터프라이즈 수준에서 통합 관리하는 운영 체계.  
* <b>II. 핵심 구성 요소:</b>  
* <b>CI/CD/CT 파이프라인:</b> 코드 통합(CI), 배포(CD), 지속적 학습(Continuous Training).  
* <b>모델 저장소(Registry):</b> 모델 버전, 메타데이터, 하이퍼파라미터 관리.  
* <b>모니터링 체계:</b> 데이터 편향(Data Drift) 및 모델 성능 저하(Concept Drift) 탐지.

* <b>III. 기대 효과:</b> AI 모델의 신속한 비즈니스 적용(Time-to-Market 단축) 및 지속적인 성능 유지.

## 3. 추정통계의 표본과 불편 추정량

* <b>I. 표본(Sample)의 개념:</b> 모집단(Population)의 통계적 특성을 추론하기 위해 모집단으로부터 추출된 부분 집합.  
* <b>II. 불편 추정량(Unbiased Estimator)의 개념:</b> 추정량의 기댓값이 모집단의 실제 모수(Parameter)와 일치하는 추정량 ($E(\hat{\theta}) = \theta$).  
* <b>III. 주요 특징:</b>  
* 편의(Bias)가 0이며, 표본의 크기가 커질수록 모수에 수렴함.  
* 표본 분산($s^2$)을 구할 때 데이터 개수 $n$이 아닌 자유도 $n-1$로 나누는 이유가 바로 표본 분산이 모분산의 '불편 추정량'이 되도록 하기 위함임.

## 4. 균형성과기록표 (BSC; Balanced Score Card)의 구성요소

* <b>I. 개념:</b> 기업의 비전과 전략을 재무적 지표와 비재무적 지표로 변환하여, 조직의 성과를 다면적이고 균형 있게 평가·관리하는 경영 프레임워크.  
* <b>II. 4대 구성 요소 (관점):</b>  
1. <b>재무적 관점 (Financial):</b> 주주와 투자자의 관점. (지표: 매출액, 영업이익률, ROI 등)  
2. <b>고객 관점 (Customer):</b> 타겟 고객 및 시장에서의 가치. (지표: 고객 만족도, 시장 점유율, 신규 고객 유치율)  
3. <b>내부 프로세스 관점 (Internal Process):</b> 고객 만족과 재무 목표 달성을 위한 내부 업무 혁신. (지표: 제조 리드타임, 불량률, 원가 절감률)  
4. <b>학습 및 성장 관점 (Learning & Growth):</b> 장기적 성장을 위한 무형 자산. (지표: 직원 교육 시간, 이직률, 정보시스템 구축 수준)

## 5. 스프링 부트 (Spring Boot)

* <b>I. 개념:</b> 복잡한 설정 없이 단독으로 실행 가능한(Stand-alone) 상용 수준의 스프링(Spring) 기반 애플리케이션을 빠르게 구축할 수 있도록 돕는 프레임워크.  
* <b>II. 주요 특징:</b>  
* <b>Auto Configuration:</b> 프로젝트에 추가된 의존성(Jar)을 기반으로 스프링 설정을 자동으로 구성.  
* <b>내장 서버 제공:</b> Tomcat, Jetty 등의 웹 서버를 내장하고 있어 별도의 서버 설치 없이 실행 가능.  
* <b>Starter POMs:</b> 특정 기능(Web, JPA 등) 구현에 필요한 라이브러리 의존성을 그룹화하여 제공.

* <b>III. 활용:</b> 생산성이 높고 독립 실행이 용이하여 마이크로서비스 아키텍처(MSA) 구현에 핵심 기술로 활용됨.

## 6. 테스트 커버리지와 코드 커버리지

* <b>I. 개념 비교:</b>  
* <b>테스트 커버리지 (Test Coverage):</b> 시스템 요구사항이나 설계 사양이 테스트에 의해 얼마나 검증되었는지를 나타내는 사용자/기능 관점의 지표 (예: 요구사항 기반 커버리지).  
* <b>코드 커버리지 (Code Coverage):</b> 소프트웨어의 소스 코드가 테스트 수행 시 얼마나 실행되었는지를 나타내는 개발자/구조 관점의 지표 (화이트박스 테스트 기법).

* <b>II. 코드 커버리지의 주요 유형:</b>  
* <b>구문(Statement):</b> 모든 코드 라인이 최소 1회 실행.  
* <b>결정(Decision/Branch):</b> 조건문의 전체 결과(True/False)가 최소 1회 실행.  
* <b>조건(Condition):</b> 조건문 내 개별 조건식이 True/False를 최소 1회 실행.  
* <b>MC/DC:</b> 개별 조건식이 다른 조건식에 독립적으로 전체 결과에 영향을 미치도록 테스트.

## 7. MongoDB의 개념 및 특징

* <b>I. 개념:</b> JSON 형식과 유사한 동적 스키마(BSON)를 사용하여 데이터를 저장하는 대표적인 문서 지향형(Document-Oriented) NoSQL 데이터베이스.  
* <b>II. 주요 특징:</b>  
* <b>데이터 구조:</b> Database > Collection > Document의 계층 구조를 가짐.  
* <b>스키마리스(Schemaless):</b> 테이블 구조를 미리 정의할 필요가 없어 비정형 데이터 처리에 매우 유연함.  
* <b>고가용성 & 확장성:</b> 레플리카 세트(Replica Set)를 통한 자동 장애 조치 및 샤딩(Sharding)을 통한 수평적 데이터 분산 처리 지원.

## 8. 변조(Modification) 와 위조(Fabrication)

* <b>I. 개념 비교 (보안 위협 형태):</b>  
* <b>변조 (Modification):</b> 인가받지 않은 자가 송수신되는 데이터나 시스템에 저장된 정보의 내용을 불법적으로 변경, 삭제, 재배열하는 공격 (주요 위협 속성: <b>무결성</b>).  
* <b>위조 (Fabrication):</b> 인가받지 않은 자가 시스템에 존재하지 않는 가짜 데이터나 트래픽을 마치 합법적인 것처럼 생성하여 삽입하는 공격 (주요 위협 속성: <b>무결성, 인증</b>).

* <b>II. 대응 방안:</b>  
* 메시지 인증 코드(MAC), 해시 함수(SHA 등), 전자 서명을 통해 데이터 무결성 및 송신자 인증 확보.

## 9. SVM (Support Vector Machine)

* <b>I. 개념:</b> 데이터 세트를 분류(Classification)하거나 회귀 분석(Regression)할 때, 클래스 간의 여백(Margin)을 최대화하는 최적의 결정 경계(초평면, Hyperplane)를 찾는 기계학습 알고리즘.  
* <b>II. 핵심 메커니즘:</b>  
* <b>서포트 벡터 (Support Vector):</b> 결정 경계와 가장 가까이 위치하여 마진의 크기를 결정하는 기준 데이터 포인트.  
* <b>커널 트릭 (Kernel Trick):</b> 선형 분리가 불가능한 데이터를 고차원 공간으로 매핑하여 선형 분류가 가능하도록 만드는 기법 (RBF 커널, 다항식 커널 등).

* <b>III. 특징:</b> 일반화 성능이 매우 뛰어나 과적합 경향이 낮지만, 데이터가 많아질수록 학습 시간이 급증함.

## 10. 과적합(Overfitting)의 발생이유와 해결방안

* <b>I. 개념:</b> 머신러닝 모델이 학습 데이터에만 과도하게 최적화되어, 새로운 데이터(테스트 데이터)에 대한 예측 및 일반화 성능이 급격히 저하되는 현상.  
* <b>II. 발생 이유:</b>  
* 학습 데이터의 양이 절대적으로 부족하거나 편향된 경우.  
* 학습 데이터 내 노이즈(이상치)까지 학습해버린 경우.  
* 모델의 매개변수가 너무 많거나 복잡도가 지나치게 높은 경우 (과도한 Epoch 반복 학습 포함).

* <b>III. 해결 방안:</b>  
* <b>데이터 측면:</b> 학습 데이터 추가 수집, 데이터 증강(Data Augmentation), 교차 검증(K-Fold Cross Validation).  
* <b>모델 측면:</b> 모델 복잡도 축소, 정규화(Regularization; L1, L2 패널티 부여), 드롭아웃(Dropout; 신경망 노드 일부 비활성화), 조기 종료(Early Stopping).

## 2교시형 문제 풀이

## 1. 소프트웨어 배포 아키텍처 및 무중단 배포 방식

### 가. 중단 배포(Downtime Deployment)의 문제점

중단 배포는 새로운 버전을 배포하기 위해 기존 서버의 구동을 멈추고 트래픽을 차단한 상태에서 업데이트를 진행하는 방식입니다.

* <b>비즈니스 연속성 단절:</b> 배포 시간 동안 서비스가 중단되어 고객 경험(UX)이 심각하게 훼손되며, 트래픽이 높은 시간대에는 매출 손실로 직결됩니다.  
* <b>롤백(Rollback)의 어려움:</b> 배포 중 치명적인 결함이 발견될 경우, 이전 버전으로 복구하는 동안에도 서비스 중단 시간이 추가로 발생합니다.  
* <b>배포 시간의 제약:</b> 서비스 영향을 최소화하기 위해 심야 시간이나 주말 등 특정 시간대에만 배포가 강제되어 개발 및 운영팀의 피로도가 증가합니다.

### 나. 무중단 배포를 위한 리버스 프록시와 로드밸런싱

무중단 배포는 사용자 트래픽의 끊김 없이 새 버전을 배포하는 기술로, 이를 위해 리버스 프록시와 로드밸런서가 필수적으로 요구됩니다.

* <b>리버스 프록시 (Reverse Proxy):</b> 클라이언트의 요청을 대신 받아 내부 서버(WAS)로 전달하는 역할을 합니다. 무중단 배포 시 내부 서버의 포트나 IP가 변경되더라도, 사용자는 리버스 프록시의 단일 엔드포인트만 바라보므로 서비스 중단 없이 트래픽 방향을 신규 버전 서버로 스위칭할 수 있습니다. (예: Nginx, Apache)  
* <b>로드밸런싱 (Load Balancing):</b> 트래픽을 여러 대의 서버로 분산시키는 기술입니다. 서버의 헬스 체크(Health Check) 기능을 통해 구버전 서버를 순차적으로 서비스에서 제외하고, 업데이트가 완료된 신버전 서버로 트래픽을 점진적으로 전환하여 다운타임을 없앱니다.

### 다. 무중단 배포 방식의 종류

| 배포 방식 | 개념 및 작동 원리 | 장점 | 단점 |
| --- | --- | --- | --- |
| <b>롤링 (Rolling)</b> | 구버전 서버를 몇 대씩 순차적으로 신버전으로 업데이트하여 점진적으로 교체하는 방식 | 추가적인 인프라 자원이 크게 필요 없음 | 배포 중 구버전과 신버전이 공존하여 호환성 문제 발생 가능 |
| <b>블루/그린 (Blue/Green)</b> | 구버전(Blue)과 동일한 규모의 신버전(Green) 환경을 미리 구축한 뒤, 로드밸런서를 통해 트래픽을 일시에 전환하는 방식 | 롤백이 매우 빠르고 구버전/신버전 공존 문제가 없음 | 시스템 자원이 정확히 2배로 필요하여 인프라 비용 증가 |
| <b>카나리 (Canary)</b> | 신버전을 소수의 사용자(또는 특정 트래픽의 1~5%)에게만 우선 배포하여 검증한 뒤, 점진적으로 전체 트래픽으로 확대하는 방식 | 실사용자 환경에서 위험을 최소화하며 A/B 테스트 가능 | 트래픽 라우팅 설정이 복잡하고 모니터링 역량이 중요함 |

## 2. 데이터베이스 튜닝 (Database Tuning)

### 가. 데이터베이스 튜닝의 개념과 목적

* <b>개념:</b> 데이터베이스 시스템이 최적의 성능을 발휘하도록 하드웨어, 운영체제, DBMS, 데이터베이스 설계, SQL 문장 등을 분석하고 개선하는 일련의 작업입니다.  
* <b>목적:</b>  
* <b>응답 시간(Response Time) 최소화:</b> 사용자의 질의에 대한 처리 결과를 빠르게 반환.  
* <b>처리량(Throughput) 극대화:</b> 단위 시간당 처리할 수 있는 트랜잭션의 수 증가.  
* <b>자원 활용 최적화:</b> CPU, 메모리(Buffer Cache), I/O 등 시스템 자원의 경합과 낭비를 줄여 안정적인 운영 보장.

### 나. 데이터베이스 설계 단계 튜닝 기법

설계 단계에서의 튜닝은 물리적 구축 이후의 튜닝보다 비용 대비 효과가 가장 큽니다.

1. <b>반정규화 (Denormalization):</b> 과도한 조인(Join)으로 인한 성능 저하를 막기 위해, 시스템 성능 향상을 목적으로 정규화된 데이터 모델을 의도적으로 중복, 병합, 분할하는 기법.  
2. <b>파티셔닝 (Partitioning):</b> 대용량 테이블을 물리적으로 여러 개의 작은 데이터 파일(Partition)로 분할하여 I/O 성능 및 관리 편의성을 향상 (Range, Hash, List 파티션 등).  
3. <b>데이터 타입 및 길이 최적화:</b> 저장 공간 낭비를 막고 메모리 처리 효율을 높이기 위해, 도메인에 맞는 최소한의 데이터 타입과 길이를 산정.  
4. <b>인덱스(Index) 설계:</b> 접근 경로를 최적화하기 위해 트랜잭션 특성과 조건절(WHERE) 빈도를 분석하여 B-Tree, Bitmap 등 적절한 인덱스를 배치.

### 다. 힌트(Hint)의 유형

힌트는 SQL 문장 내에 삽입되어 옵티마이저(Optimizer)의 실행 계획 수립에 개발자가 직접 개입하는 지시어입니다.

* <b>최적화 목표 힌트:</b> `/*+ ALL_ROWS */` (전체 처리 속도 최적화), `/*+ FIRST_ROWS */` (최초 응답 속도 최적화).  
* <b>액세스 경로 힌트:</b> `/*+ FULL(table) */` (풀 테이블 스캔), `/*+ INDEX(table index_name) */` (특정 인덱스 스캔 유도).  
* <b>조인 순서 힌트:</b> `/*+ ORDERED */` (FROM 절에 기술된 순서대로 조인), `/*+ LEADING(table1 table2) */` (특정 테이블을 먼저 조인하도록 유도).  
* <b>조인 방식 힌트:</b> `/*+ USE_NL(table) */` (Nested Loop 조인), `/*+ USE_HASH(table) */` (Hash 조인), `/*+ USE_MERGE(table) */` (Sort Merge 조인).

## 3. 개인정보 안전성 확보 조치 기준: 내부관리계획

* <b>정의:</b> 개인정보처리자가 개인정보를 분실, 도난, 유출, 위조, 변조 또는 훼손되지 않도록 안전하게 처리하기 위하여 조직의 특성에 맞게 수립하고 시행하는 내부 기준 및 관리 규정입니다. (개인정보 보호법 제29조 근거).  
* <b>필요성:</b>  
* <b>컴플라이언스 준수:</b> 법적 의무 사항으로, 미수립 시 과태료 처분 대상.  
* <b>책임과 역할 명확화:</b> 조직 내 개인정보 처리 및 보안에 대한 권한과 책임을 투명하게 할당.  
* <b>체계적인 보안 통제:</b> 인적, 물리적, 기술적 보안 조치의 기준점이 되어 임직원의 보안 인식을 제고하고 사고를 예방.

* <b>주요 내용:</b>  
1. 개인정보 보호책임자(CPO)의 지정에 관한 사항.  
2. 개인정보 보호책임자 및 취급자의 역할 및 책임에 관한 사항.  
3. 개인정보의 안전성 확보에 필요한 조치 이행에 관한 사항 (접근 통제, 암호화, 접속기록 보관 등).  
4. 개인정보 취급자에 대한 교육에 관한 사항.  
5. 그 밖에 개인정보 보호를 위하여 필요한 사항.

## 4. 데이터 거버넌스와 마스터 데이터 관리

### 가. 데이터 거버넌스(Data Governance)의 개념 및 주요 기능

* <b>개념:</b> 전사 차원의 모든 데이터에 대하여 정책, 지침, 표준, 전략 및 방향을 수립하고, 데이터를 관리·통제하는 조직과 프로세스를 구축하는 프레임워크입니다.  
* <b>주요 기능:</b>  
* <b>데이터 표준화:</b> 명명 규칙, 용어 사전, 도메인 정의.  
* <b>데이터 품질 관리:</b> 데이터의 정확성, 완전성, 일관성 등을 측정하고 개선.  
* <b>보안 및 프라이버시 관리:</b> 권한 제어, 데이터 마스킹, 컴플라이언스 준수.  
* <b>생명주기 관리:</b> 데이터의 생성, 활용, 보관, 폐기까지의 흐름 통제.

### 나. 마스터 데이터(Master Data)의 개념과 필요성

* <b>개념:</b> 기업의 비즈니스 수행에 필수적이고 공통적으로 사용되는 핵심 기준 데이터 (예: 고객, 상품, 부서, 공급업체 정보).  
* <b>필요성:</b> 시스템별로 파편화된 데이터로 인한 사일로(Silo) 현상을 방지하고, 전사적으로 단일 진실 공급원(SSOT; Single Source of Truth)을 제공하여 의사결정의 신뢰성과 업무 효율성을 높이기 위해 필요합니다.

### 다. 마스터 데이터 관리 (MDM) 구성요소와 구축 시 고려사항

* <b>구성요소:</b>  
* <b>데이터 사전 (Data Dictionary):</b> 마스터 데이터의 메타데이터 및 속성 정의.  
* <b>정제 엔진 (Cleansing Engine):</b> 중복 제거, 오류 수정, 포맷 통일.  
* <b>통합 저장소 (MDM Hub):</b> 정제된 황금 레코드(Golden Record)를 저장.  
* <b>연계 인터페이스:</b> 레거시 시스템과 MDM 간 데이터 동기화 기능.

* <b>구축 시 고려사항:</b>  
* IT 부서 중심이 아닌 현업(비즈니스 부서) 중심의 <b>오너십(Ownership) 부여</b>가 필수적입니다.  
* 빅뱅 방식보다는 핵심 도메인(예: 고객, 상품)부터 점진적으로 구축하여 리스크를 최소화해야 합니다.  
* 구축 이후에도 품질이 저하되지 않도록 상시적인 데이터 거버넌스 체계와 맞물려 운영되어야 합니다.

## 5. 데이터베이스 옵티마이저 (Optimizer)

### 가. 옵티마이저의 개념

옵티마이저는 사용자가 요청한 SQL 문장을 해석하여, 데이터를 가장 효율적이고 빠르게 추출할 수 있는 '최적의 실행 계획(Execution Plan)'을 결정하는 DBMS의 핵심 엔진입니다.

### 나. RBO(Rule Based Optimizer)와 CBO(Cost Based Optimizer) 비교

| 구분 | RBO (규칙 기반 옵티마이저) | CBO (비용 기반 옵티마이저) |
| --- | --- | --- |
| <b>판단 기준</b> | DBMS에 사전 정의된 <b>우선순위 규칙(Rule)</b> | 통계 정보를 바탕으로 산출된 <b>예상 비용(Cost)</b> |
| <b>핵심 요소</b> | 인덱스 유무, 연산자 종류, SQL 작성 순서 | 테이블 크기, 레코드 수, 인덱스 분포도, I/O 비용 |
| <b>장점</b> | 실행 계획이 예측 가능하여 개발자의 의도대로 제어 용이 | 데이터의 실제 특성을 반영하므로 대용량/복잡한 쿼리에 효율적 |
| <b>단점</b> | 데이터 분포와 양을 무시하여 비효율적 실행 계획 생성 가능 | 통계 정보가 오래되거나 부정확할 경우 최악의 실행 계획 생성 가능 |
| <b>활용 현황</b> | 과거 시스템 (현재는 하위 호환성 목적으로만 존재) | 현대 DBMS의 표준 (오라클, MySQL, PostgreSQL 등) |

## 6. 소프트웨어 정의 네트워크 (SDN; Software Defined Network)

### 가. SDN 제어평면(Control Plane)의 개요 및 구조적 특징

* <b>개요:</b> 기존 네트워크 장비(라우터, 스위치)에서 패킷 포워딩(Data Plane)과 경로 제어(Control Plane) 기능을 분리한 후, 제어 기능을 중앙의 소프트웨어 기반 컨트롤러로 집중시킨 구조입니다.  
* <b>구조적 특징:</b>  
* <b>중앙 집중형 논리 제어:</b> 네트워크 전체의 상태 뷰(Global View)를 컨트롤러가 확보하여 일관된 정책 렌더링이 가능.  
* <b>인터페이스 분리:</b>  
* <b>Northbound API:</b> 애플리케이션 계층(방화벽, 로드밸런서 등)과 컨트롤러 간 통신 (주로 REST API 사용).  
* <b>Southbound API:</b> 컨트롤러와 인프라 계층(물리/논리 스위치) 간 통신 (Openflow 등).

### 나. 오픈플로우 (Openflow) 프로토콜

* <b>개념:</b> SDN 구조에서 제어평면(컨트롤러)과 데이터평면(스위치) 간의 통신을 위해 ONF(Open Networking Foundation)에서 정의한 Southbound API의 표준 프로토콜.  
* <b>주요 특징:</b>  
* <b>플로우 테이블 (Flow Table):</b> 패킷의 매칭 조건(Match Fields)과 수행할 액션(Action; 전달, 폐기, 수정 등)을 정의한 규칙 테이블을 스위치에 내려보냅니다.  
* <b>보안 채널 (Secure Channel):</b> 컨트롤러와 스위치 간 통신은 TLS 기반의 안전한 채널을 통해 이루어집니다.

## 7. SOAR (Security Orchestration, Automation and Response)

* <b>개념:</b> 다양한 보안 솔루션에서 발생하는 경보를 중앙에서 수집하고, 표준화된 대응 절차(Playbook)에 따라 침해 사고 대응을 자동화 및 오케스트레이션하는 지능형 보안 플랫폼.  
* <b>등장 배경:</b>  
* SIEM 등의 도입으로 수많은 보안 알람이 발생하여 보안 담당자의 피로도(Alert Fatigue) 급증.  
* 전문 인력 부족 및 파편화된 이기종 보안 솔루션으로 인한 수동 대응의 한계와 지연 시간(MTTR) 증가.

* <b>구성요소 및 주요 기능:</b>  
1. <b>SOA (Security Orchestration & Automation):</b> 이기종 보안 솔루션의 API를 연동하여 워크플로우와 플레이북(Playbook) 기반으로 자동 대응 수행.  
2. <b>SIRP (Security Incident Response Platform):</b> 침해 사고 발생부터 완료까지의 전 과정을 티켓팅 시스템을 통해 관리하고 추적.  
3. <b>TIP (Threat Intelligence Platform):</b> 외부의 위협 정보(IoC 등)를 수집, 분석하여 내부 경보의 정탐 여부를 검증하고 대응 전략에 반영.

* <b>기대효과:</b> 오탐 필터링 자동화 및 초동 대응 시간 획기적 단축, 대응 프로세스의 표준화로 인한 인적 역량 편차 해소.  
* <b>도입 시 고려사항:</b> 자사 환경에 맞는 정확한 Playbook 개발 역량 확보, 기존 레거시 보안 인프라(방화벽, 백신, SIEM)와의 원활한 API 연동성 사전 검토.

## 8. MSA (Micro Service Architecture)

### 가. MSA 개념 및 특징과 구현 원칙

* <b>개념:</b> 크고 복잡한 애플리케이션을 비즈니스 기능(Domain) 단위로 독립적으로 배포 가능한 작고 느슨하게 결합된 서비스들의 모음으로 구축하는 아키텍처.  
* <b>특징:</b> 독립적 배포, 폴리글랏(Polyglot; 서비스별 최적의 언어 및 DB 선택), 장애 격리.  
* <b>구현 시 지켜야 할 원칙:</b>  
* <b>Bounded Context:</b> 도메인 주도 설계(DDD)를 기반으로 서비스 간 경계를 명확히 정의.  
* <b>Decentralized Data:</b> 서비스별로 독립된 데이터베이스를 보유하여 결합도를 낮춤.  
* <b>API Gateway 도입:</b> 클라이언트와 마이크로서비스 간의 단일 진입점을 구성하여 라우팅, 인증, 모니터링 수행.

### 나. 모놀리스 아키텍처와 MSA 비교

| 구분 | Monolith Architecture | Micro Service Architecture (MSA) |
| --- | --- | --- |
| <b>구조</b> | 모든 기능이 하나의 애플리케이션(프로젝트)에 결합 | 기능별로 서비스가 분리되어 API로 통신 |
| <b>배포 및 확장</b> | 일부분 수정 시 전체를 재배포, 전체 스케일 아웃만 가능 | 수정된 특정 서비스만 독립 배포 및 개별 스케일 아웃 가능 |
| <b>기술 스택</b> | 단일 언어, 단일 데이터베이스 종속 | 서비스 특성에 맞는 다양한 언어와 DB 선택 (Polyglot) |
| <b>장애 영향</b> | 특정 기능의 장애(메모리 누수 등)가 전체 시스템 중단 유발 | 특정 서비스 장애가 다른 서비스로 전파되지 않음 (장애 격리) |
| <b>복잡도</b> | 초기 개발 단순, 유지보수 시 코드 복잡도 기하급수적 증가 | 분산 시스템 특성상 트랜잭션, 테스트, 배포 관리가 매우 복잡함 |

### 다. MSA 구현을 위한 서비스 매시 (Service Mesh)

* <b>개념:</b> 마이크로서비스 간의 복잡한 통신(트래픽 제어, 보안, 모니터링)을 서비스 코드에서 분리하여 인프라 계층에서 처리하는 아키텍처 패턴입니다.  
* <b>특징:</b> 주로 각 서비스 컨테이너에 프록시를 <b>사이드카(Sidecar)</b> 형태로 붙여 네트워크 통신을 대행합니다. (대표 기술: Istio, Linkerd) 개발자는 비즈니스 로직에만 집중할 수 있으며, 통신 안정성과 관측성(Observability)을 확보할 수 있습니다.

## 9. 데이터베이스 샤딩 (Sharding)

### 가. 샤딩의 개념 및 분할 방법

* <b>개념:</b> 데이터베이스 트래픽과 용량의 한계를 극복하기 위해, 대용량의 데이터를 여러 대의 독립적인 물리적 데이터베이스 서버(Shard)에 수평적으로 분할(Horizontal Partitioning)하여 분산 저장하는 기술 (Scale-out).  
* <b>분할 방법 (Sharding Key 알고리즘):</b>  
* <b>Hash Sharding:</b> 샤딩 키를 해시 함수에 통과시켜 나온 결과값으로 서버를 결정. (데이터 분산은 균일하나 서버 증설 시 재배치가 어려움)  
* <b>Range Sharding:</b> 값의 범위(예: 날짜, 회원번호)를 기준으로 서버를 분할. (조회가 빠르나 특정 서버에 트래픽이 몰릴 수 있음)  
* <b>Directory Sharding:</b> 별도의 룩업 테이블(Directory)을 두어 샤딩 키와 해당 Shard 위치를 매핑. (유연성이 가장 높으나 룩업 테이블이 병목이 될 수 있음)

### 나. 샤딩과 파티셔닝(Partitioning)의 차이점

* <b>샤딩:</b> 물리적으로 <b>서로 다른 데이터베이스 노드(서버)</b> 간에 데이터를 분할. 시스템 부하를 여러 하드웨어 자원으로 분산(Scale-out)하는 데 초점.  
* <b>파티셔닝:</b> 물리적/논리적으로 <b>동일한 단일 데이터베이스 노드 내부</b>에서 테이블을 쪼개어 저장. 인덱스 크기를 줄이고 단일 서버 내 파일 I/O를 최적화(Scale-up 효율성)하는 데 초점.

### 다. 샤딩 적용 시 고려사항

* <b>Cross-Shard Join 불가:</b> 서로 다른 Shard에 있는 데이터 간의 조인이 사실상 불가능하므로, 데이터 중복 저장(비정규화)이나 애플리케이션 레벨의 조합이 필요.  
* <b>글로벌 기본키(Global PK) 충돌:</b> Auto Increment 속성을 각 Shard가 독립적으로 사용하면 PK가 중복될 수 있으므로, UUID나 별도의 글로벌 키 생성 전략(예: Snowflake) 필수.  
* <b>Re-balancing:</b> 특정 Shard로 데이터가 편중(Hotspot)되거나 노드가 추가될 때, 무중단으로 데이터를 재분배하는 전략이 매우 복잡함.

## 10. 블록(Block) 암호 모드

블록 암호는 평문을 일정한 크기(Block)로 자르고 각 블록을 암호화하는 방식입니다. 블록보다 긴 평문을 암호화하기 위해 여러 블록을 연결하는 방식을 운영 모드(Operation Mode)라고 합니다.

### 가. ECB (Electronic CodeBook) 모드

* <b>방식:</b> 평문을 블록 단위로 나누어 각각 독립적으로 동일한 키를 사용하여 암호화합니다.  
* <b>특징:</b> 구현이 가장 단순하고 병렬 처리가 가능합니다. 하지만 평문 블록이 같으면 암호문 블록도 완전히 동일하게 출력되어 <b>데이터의 패턴이 그대로 노출</b>되므로 현재는 사용이 권장되지 않습니다.

### 나. CBC (Cipher Block Chaining) 모드

* <b>방식:</b> 현재의 평문 블록을 이전 블록의 암호문과 XOR 연산한 후 암호화합니다. (첫 블록은 초기화 벡터(IV) 사용).  
* <b>특징:</b> 동일한 평문 블록이라도 이전 암호문의 영향을 받아 다른 암호문이 생성되므로 안전성이 높습니다. 단, 암호화는 순차적으로 진행되어야 하므로 병렬 처리가 불가능하며, 한 블록의 에러가 다음 블록에 파급(Error Propagation)됩니다.

### 다. CFB (Cipher FeedBack) 모드

* <b>방식:</b> 이전 암호문 블록을 암호화한 결과와 현재의 평문 블록을 XOR 연산하여 현재의 암호문 블록을 생성합니다. 블록 암호 알고리즘을 스트림 암호처럼 사용합니다.  
* <b>특징:</b> 패딩(Padding)이 필요하지 않으며, 실시간으로 전송되는 1비트 단위의 데이터 암호화에 적합합니다. CBC와 마찬가지로 암호화의 병렬 처리는 불가합니다.

### 라. OFB (Output FeedBack) 모드

* <b>방식:</b> 평문과 독립적으로 초기화 벡터(IV)를 연속적으로 암호화하여 키 스트림(Key Stream)을 만들고, 이를 평문과 XOR 연산하여 암호문을 생성합니다.  
* <b>특징:</b> 평문이 암호화 과정의 입력으로 들어가지 않으므로, 전송 중 암호문에 비트 오류가 발생해도 복호화 시 해당 비트에만 오류가 발생하고 다음 블록으로 파급되지 않습니다. (음성, 영상 등 노이즈가 있는 채널 통신에 유리).

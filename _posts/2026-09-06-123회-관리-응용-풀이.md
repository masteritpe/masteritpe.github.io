## 1교시형 문제 풀이

## 1. SCRUM의 팀구성 및 개발프로세스

애자일(Agile) 대표 프레임워크인 스크럼(SCRUM)은 신속한 주기와 자율적 팀 구성을 통해 작동 가능한 소프트웨어를 반복적으로 출시하는 소프트웨어 개발 방식이다.

<b>SCRUM 팀 구성</b>

* <b>Product Owner (PO)</b>: 제품 백로그(Product Backlog) 작성 및 우선순위 지정, 비즈니스 가치 극대화 책임.  
* <b>Scrum Master (SM)</b>: 스크럼 원칙 준수 조력자, 외부 방해 요소 및 내부 장애물(Impediments) 제거.  
* <b>Developers (개발팀)</b>: Cross-functional 팀으로 매 스프린트마다 실행 가능한 결과물(Increment)을 직접 개발.

<b>개발 프로세스 (Sprint Lifecycle)</b>

* <b>Product Backlog 수립</b>: PO가 사용자 요구사항을 기반으로 구현할 기능의 우선순위 목록 작성.  
* <b>Sprint Planning</b>: 스프린트 목표 설정 및 Product Backlog에서 이번 주기에 수행할 Sprint Backlog 도출.  
* <b>Sprint 실행 & Daily Scrum</b>: 1~4주 단위 개발 진행, 매일 15분간 일일 스크럼을 통해 진행 상황 및 장애 요소 공유.  
* <b>Sprint Review</b>: 스프린트 종료 시 이해관계자에게 완성된 산출물(Increment)을 시연하고 피드백 수렴.  
* <b>Sprint Retrospective</b>: 해당 스프린트의 개발 프로세스, 도구, 협업 방식을 회고하여 다음 주기의 개선점 도출.

## 2. 타당도(Validity)와 신뢰도(Reliability)

측정도구가 측정하고자 하는 개념을 얼마나 정확히 측정하는가(타당도)와 얼마나 일관되게 측정하는가(신뢰도)를 나타내는 데이터 평가 지표이다.

| 구분 | 타당도 (Validity) | 신뢰도 (Reliability) |
| --- | --- | --- |
| <b>개념</b> | 측정도구가 측정 대상의 본질을 정확히 반영하는 정도 | 동일한 대상에 대해 반복 측정 시 일관된 결과를 얻는 정도 |
| <b>핵심 질문</b> | "측정하고자 하는 것을 올바르게 측정하고 있는가?" | "재측정 시 동일한 결과가 도출되는가?" |
| <b>평가 방법</b> | 내용 타당도, 기준 타당도, 구인 타당도, 내적/외적 타당도 | 재검사 신뢰도, 동형검사 신뢰도, 반분 신뢰도, Cronbach's $\alpha$ |
| <b>주요 오차</b> | 체계적 오차(Systematic Error) 제어 | 무작위 오차(Random Error) 제어 |
| <b>상호 관계</b> | 신뢰도는 타당도의 필요조건 (신뢰도 없이 타당도 확보 불가) | 타당도는 신뢰도의 충분조건이 아님 (일관성이 있어도 타당도가 낮을 수 있음) |

## 3. 디파이(De-Fi: Decentralized Finance)

블록체인과 스마트 계약(Smart Contract)을 기반으로 중앙화된 금융 중개기관 없이 제공되는 P2P 방식의 탈중앙화 금융 서비스 시스템이다.

<b>핵심 구성요소 및 메커니즘</b>

* <b>Smart Contract</b>: 사전 정의된 금융 거래 조건을 중개자 없이 자동 실행하는 코드.  
* <b>DEX (탈중앙화 거래소)</b>: AMM(Automated Market Maker) 알고리즘 기반으로 매수/매도자 간 직접 암호자산 교환 지원.  
* <b>Lending & Yield Farming</b>: 암호자산 담보 대출 및 유동성 공급에 따른 이자·토큰 보상 수령 메커니즘.  
* <b>Oracle</b>: 온체인 스마트 계약에 외부 실세계 시세 데이터 등을 안전하게 제공하는 데이터 연계 미들웨어.

<b>주요 위험요인</b>

* <b>스마트 계약 취약점</b>: 코드 버그로 인한 정산 오류 및 오라클 공격 위험.  
* <b>루그풀(Rug Pull)</b>: 유동성 공급 자금을 강제로 인출해 수거해가는 사기 위험.

## 4. HAZOP (HAZard and OPerability analysis)

산업 공정 및 복잡한 시스템의 위험요소(Hazard)와 운전상의 문제점(Operability)을 도출하기 위해 공정 변수에 가이드워드(Guide Words)를 체계적으로 적용하는 정성적 위험성 평가 기법이다.

<b>HAZOP 분석 절차</b>

* <b>Node 선정</b>: 공정 흐름도(P&ID)를 기준으로 분석 최소 단위(Node) 설정.  
* <b>Parameter & Guide Word 조합</b>: 공정 변수(온도, 압력, 유량 등)에 가이드워드를 결합하여 이탈(Deviations) 도출.  
* <b>원인/결과 분석 및 대책 수립</b>: 이탈의 원인과 영향을 정성적으로 평가한 후 예방 안전 대책 제안.

<b>주요 가이드워드</b>

| Guide Word | 의미 | 예시 (유량 Parameter 적용 시) |
| --- | --- | --- |
| <b>No / Not</b> | 설계 의도의 완전한 부정 | 유량 없음 (No Flow) |
| <b>More / Less</b> | 양적 증가 또는 감소 | 고유량 (More) / 저유량 (Less) |
| <b>As Well As</b> | 질적 증가 (다른 물질 첨가) | 불순물 또는 유기용매 유입 |
| <b>Part Of</b> | 질적 감소 (일부 성분 누락) | 혼합액의 특정 성분 결여 |
| <b>Reverse</b> | 설계 의도와 반대 방향 작용 | 유체의 역류 (Reverse Flow) |
| <b>Other Than</b> | 완벽한 대체 (전혀 다른 상태) | 설계와 다른 종류의 액체 유입 |

## 5. 능동 학습(Active Learning)

라벨링되지 않은 데이터 중 모델 학습에 가장 유용한 샘플을 모델이 능동적으로 추출하여 사람(Oracle)에게 라벨링을 요청하는 머신러닝 기법이다.

<b>능동 학습 프로세스</b>

* <b>Initial Training</b>: 소량의 라벨링 데이터로 기본 예측 모델 학습.  
* <b>Querying</b>: 라벨링되지 않은 데이터 풀에서 추출 전략에 따라 가장 학습 가치가 높은 데이터 선정.  
* <b>Annotation & Retraining</b>: 전문가(Oracle)가 선별된 데이터에 라벨을 부여하고, 데이터셋에 추가하여 모델 재학습 반복.

<b>주요 데이터 추출 전략 (Query Strategies)</b>

* <b>Uncertainty Sampling</b>: 모델이 예측 결과를 가장 확신하지 못하는 데이터 추출 (Least Confidence, Entropy).  
* <b>Query-By-Committee (QBC)</b>: 여러 모델(Committee) 간 예측 결과의 불일치(Disagreement)가 가장 큰 데이터 선택.  
* <b>Expected Model Change</b>: 학습 적용 시 모델 가중치를 가장 크게 변화시킬 것으로 예상되는 데이터 선택.

## 6. Wi-Fi 6E

기존 Wi-Fi 6(802.11ax)의 핵심 기술을 유지하면서, 신규 주파수 대역인 6GHz 대역(5.925GHz ~ 7.125GHz)까지 확장한 무선 랜 규격이다.

<b>주요 특징</b>

* <b>6GHz 신규 대역 확보</b>: 최대 1,200MHz 대역폭을 추가 확보하여 2.4GHz/5GHz 대역의 채널 포화 및 신호 간섭 문제 해결.  
* <b>채널 확장성</b>: 160MHz 초고속 대역폭 채널을 최대 7개까지 제공(기존 5GHz는 2개).  
* <b>Wi-Fi 6 핵심 기술 탑재</b>: OFDMA, MU-MIMO, 1024-QAM, Target Wake Time(TWT), BSS Coloring 등 동일 지원.

<b>Wi-Fi 6 vs Wi-Fi 6E 비교</b>

| 구분 | Wi-Fi 6 | Wi-Fi 6E |
| --- | --- | --- |
| <b>지원 주파수</b> | 2.4 GHz, 5 GHz | <b>2.4 GHz, 5 GHz, 6 GHz</b> |
| <b>160MHz 채널 수</b> | 2개 | <b>최대 7개</b> |
| <b>간섭 영향</b> | 레거시(Wi-Fi 4/5) 기기와 채널 경합 존재 | 6GHz 전용 기기만 접근하여 간섭 최소화 |
| <b>주요 활용</b> | 일반 고속 무선 LAN | 8K 스트리밍, AR/VR, 초저지연 업무 환경 |

## 7. 산업제어시스템(ICS) 보안 구조와 ICT 시스템 비교

OT(Operational Technology) 기반 산업제어시스템(SCADA, DCS, PLC)은 물리적 공정 제어를 목적으로 하여, 데이터 중심의 ICT(IT) 시스템과 보안 우선순위 및 가동 환경에서 차이를 보인다.

<b>ICS 보안 vs ICT 시스템 비교</b>

| 구분 | 산업제어시스템 (ICS/OT) | ICT 시스템 (IT) |
| --- | --- | --- |
| <b>보안 목표 우선순위</b> | <b>가용성(A) > 무결성(I) > 기밀성(C)</b> | <b>기밀성(C) > 무결성(I) > 가용성(A)</b> |
| <b>수명 주기</b> | 10년 ~ 20년 이상 (장기 운용) | 3년 ~ 5년 (주기적 교체) |
| <b>패치 및 업데이트</b> | 연속 운용 필요성으로 패치 적용 제약 | 정기 및 임시 보안 패치 수시 적용 가능 |
| <b>가동 제약</b> | 24/7/365 무휴지 가동 (Zero Downtime) | 다운타임 및 정기점검 허용 가능 |
| <b>사고 발생 시 영향</b> | 인명 사고, 공정 중단, 물리적 설비 파괴 | 정보 유출, 데이터 훼손, 금전 손실 |

<b>ICS 보안 아키텍처 (Purdue Model 기반 계층적 심층방어)</b>

* <b>Level 0~2 (제어구역)</b>: Sensor, PLC, HMI 구역. 폐쇄망 운영 및 물리적 통제.  
* <b>Level 3 (운영구역)</b>: SCADA, MES 구역. 제어망과 상위망 간 방화벽 및 인가 통제.  
* <b>Level 3.5 (Industrial DMZ)</b>: OT망과 IT망 사이의 완충 구역. 데이터 전송용 히스토리안 서버 및 Jump Host 배치.  
* <b>Level 4~5 (기업 IT 구역)</b>: ERP, 일반 사무망 영역.

## 8. 지식 증류(Knowledge Distillation)

거대하고 복잡한 교사 모델(Teacher Model)이 학습한 지식을 경량화된 학생 모델(Student Model)로 이전하여, 성능 저하를 최소화하면서 모델 크기와 추론 속도를 최적화하는 모델 압축 기술이다.

<b>동작 메커니즘</b>

* <b>Soft Target 생성</b>: Teacher Model의 Logit 출력에 온도 파라미터 $T$ (Temperature)를 적용하여 클래스 간 확률 분포(Soft Target) 계산.

$$\text{Softmax}(z_i / T) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

* <b>손실 함수(Loss Function) 연산</b>: Student Model은 실제 정답(Hard Label)과의 Cross-Entropy Loss와 Teacher의 Soft Target과의 Distillation Loss를 합성하여 학습.

$$L_{total} = \alpha L_{CE} + (1-\alpha) T^2 L_{KD}$$

<b>주요 형태</b>

* <b>Response-based</b>: 교사 모델의 최종 출력 확률 분포 학습.  
* <b>Feature-based</b>: 교사 모델 중간 레이어의 특징 맵(Feature Map) 정보 이전.  
* <b>Relation-based</b>: 데이터 샘플 간의 상호 관계 구조 학습.

## 9. IEC 61508 - 안전 무결성 수준(SIL: Safety Integrity Level)

전기/전자/프로그래머블 전자(E/E/PE) 안전 관련 시스템의 기능 안전(Functional Safety)을 정의하는 국제 표준 IEC 61508의 위험 감소 및 안전 성능 등급 지표이다.

<b>안전 무결성 수준 개요</b>

* SIL은 1부터 4까지 4단계로 구분되며, <b>SIL 4</b>가 가장 높은 수준의 안전 무결성을 나타냄.  
* 시스템 운전 모드에 따라 평가 기준 구분:  
* <b>저빈도 운전 모드 (Low Demand Mode)</b>: 연 1회 이하 동작 (비상 정지 시스템 등). 요구 시 평균 실패 확률($PFD_{avg}$) 기준.  
* <b>고빈도 / 연속 운전 모드 (High/Continuous Demand Mode)</b>: 상시 제어 시스템. 시간당 위험 실패 확률($PFH$) 기준.

<b>SIL 단계별 등급 기준</b>

| SIL 등급 | 저빈도 모드 ($PFD_{avg}$) | 고빈도/연속 모드 ($PFH$) | 위험 감소율 (Risk Reduction) |
| --- | --- | --- | --- |
| <b>SIL 4</b> | $\ge 10^{-5} \text{ to } &lt; 10^{-4}$ | $\ge 10^{-9} \text{ to } &lt; 10^{-8}$ | $10,000 \sim 100,000$ 배 감소 |
| <b>SIL 3</b> | $\ge 10^{-4} \text{ to } &lt; 10^{-3}$ | $\ge 10^{-8} \text{ to } &lt; 10^{-7}$ | $1,000 \sim 10,000$ 배 감소 |
| <b>SIL 2</b> | $\ge 10^{-3} \text{ to } &lt; 10^{-2}$ | $\ge 10^{-7} \text{ to } &lt; 10^{-6}$ | $100 \sim 1,000$ 배 감소 |
| <b>SIL 1</b> | $\ge 10^{-2} \text{ to } &lt; 10^{-1}$ | $\ge 10^{-6} \text{ to } &lt; 10^{-5}$ | $10 \sim 100$ 배 감소 |


## 2교시형 문제 풀이

## 1. 다변량 데이터 차원 축소 분석기법

### 가. 변수의 차원을 줄이는 다변량회귀분석 (Multivariate Regression Analysis)

* <b>개념</b>: 여러 개의 독립변수($X$)와 여러 개의 종속변수($Y$) 간의 선형적 연관성을 동시에 모델링하는 통계 기법이다.  
* <b>차원 축소 메커니즘</b>: 다중공선성(Multicollinearity)이 존재하는 수많은 독립변수 중 종속변수에 유의미한 영향력을 미치는 핵심 변수만을 단계적 선택법(Stepwise), 전진 선택법(Forward Selection), 또는 Lasso/Ridge 규제화(Regularization)를 통해 선별함으로써 설명력의 손실을 최소화하며 다대다(M:N) 관계의 변수 차원을 축소한다.

$$Y_{m \times q} = X_{m \times (p+1)} \beta_{(p+1) \times q} + \epsilon_{m \times q}$$

### 나. 변수의 차원을 줄이는 주성분분석 (PCA: Principal Component Analysis)

* <b>개념</b>: 고차원 공간에 존재하는 수치형 변수 간의 상관관계를 기반으로, 데이터의 분산(Variance)을 가장 잘 보존하는 직교 축(Orthogonal Axis)을 찾아 저차원 공간으로 선형 변환하는 비지도 학습 기법이다.  
* <b>차원 축소 메커니즘</b>: 데이터의 공분산 행렬(Covariance Matrix)을 고유값 분해(Eigen Decomposition)하여 고유값(Eigenvalue)과 고유벡터(Eigenvector)를 구한다. 분산의 크기가 가장 큰 순서대로 주성분(Principal Component)을 선택하여 원래 변수의 개수 $p$보다 적은 $k$개($k \ll p$)의 서로 독립인 합성 변수(Linear Combination)로 차원을 축소한다.

### 다. 케이스의 차원을 줄이는 다차원척도법 (MDS: Multidimensional Scaling)

* <b>개념</b>: 개체(Case/Subject) 간의 비유사성(Dissimilarity)이나 거리(Distance) 데이터를 활용하여 개체들을 저차원(주로 2D 또는 3D) 공간에 점으로 시각화 배치하는 분석 기법이다.  
* <b>차원 축소 메커니즘</b>: 고차원에 존재하는 $N$개 개체 간의 실제 거리($d_{ij}$)와 저차원 공간으로 투영된 거리($\hat{d}_{ij}$) 간의 오차를 나타내는 Stress 지표를 최소화한다. 고차원의 개체(Case) 집합을 인간이 직관적으로 인식할 수 있는 저차원 평면 좌표로 투영하여 개체 간 잠재 구조 및 유사성 집단을 도출한다.

$$\text{Stress} = \sqrt{\frac{\sum (d_{ij} - \hat{d}_{ij})^2}{\sum d_{ij}^2}}$$

## 2. 기술통계와 추론통계

### 가. 기술통계와 추론통계의 차이점 비교

| 구분 | 기술통계 (Descriptive Statistics) | 추론통계 (Inferential Statistics) |
| --- | --- | --- |
| <b>개념</b> | 수집된 데이터의 특성을 요약, 정리, 시각화하여 표현하는 통계 기법 | 표본(Sample) 데이터를 바탕으로 모집단(Population)의 특성을 확률적으로 추정 및 검정하는 기법 |
| <b>주요 목적</b> | 데이터의 현황 파악 및 요약 | 모집단 추론, 가설 검정, 미래 예측 |
| <b>분석 대상</b> | 관측된 표본 또는 데이터 집합 자체 | 관측되지 않은 전체 모집단 |
| <b>결과의 성격</b> | 확정적 사실 (오차 확률 미포함) | 확률적 추정 (유의수준, 신뢰구간, 오차범위 포함) |
| <b>핵심 매개체</b> | 대푯값, 산포도, 그래프 | 가설(Null/Alternative Hypothesis), 확률 distribution ($p$-value) |

### 나. 기술통계와 추론통계에 사용되는 기술

<b>기술통계에 사용되는 기술 (4가지)</b>

* <b>중심경향치 측정 (Central Tendency)</b>: 데이터의 중심 위치를 나타내는 지표 (평균, 중앙값, 최빈값).  
* <b>산포도 측정 (Dispersion)</b>: 데이터가 중심으로부터 퍼져있는 정도 측정 (분산, 표준편차, 사분위수 범주, 범위).  
* <b>빈도 분석 및 수치 요약 (Frequency Distribution)</b>: 데이터 구간별 빈도, 상대빈도, 누적빈도를 나타내는 교차표 및 빈도표 구성.  
* <b>시각화 기법 (Data Visualization)</b>: 데이터 분포 및 이상치를 직관적으로 파악하기 위한 그래프 표현 (히스토그램, 박스플롯, 줄기-잎 그림).

<b>추론통계에 사용되는 기술 (4가지)</b>

* <b>모수 추정 (Point & Interval Estimation)</b>: 표본 통계량을 바탕으로 모집단의 모수(모평균, 모비율 등)를 점추정하거나 신뢰구간(Confidence Interval)으로 추정하는 기술.  
* <b>가설 검정 (Hypothesis Testing)</b>: 귀무가설($H_0$)과 대립가설($H_1$)을 설정하고 $t$-검정, ANOVA($F$-검정) 등을 이용해 $p$-value를 산출하여 가설 채택 여부를 결정하는 기법.  
* <b>카이제곱 검정 (Chi-Square Test)</b>: 범주형 변수 간의 독립성 검정 및 적합도 검정을 수행하는 교차 분석 기법.  
* <b>회귀 분석 (Regression Analysis)</b>: 독립변수와 종속변수 간의 인과관계를 추정하고 모형의 유의성을 검정하는 통계적 모델링 기법.

## 3. API Gateway의 역할, 필요성, 주요기능, 고려사항 및 적용사례

### 가. API Gateway의 역할 및 필요성

* <b>개념</b>: 클라이언트 프로그램과 백엔드 마이크로서비스(Microservices) 집합 사이에서 단일 진입점(Single Point of Entry) 역할을 수행하는 API 프록시 서버이다.  
* <b>역할</b>: 클라이언트의 요청을 알맞은 내부 서비스로 엔드포인트를 라우팅하고, 서비스 간 공통 관심사(Cross-cutting Concerns)를 중앙에서 일괄 처리한다.  
* <b>필요성</b>:  
* <b>엔드포인트 단일화</b>: 클라이언트가 다수의 마이크로서비스 주소를 개별 관리해야 하는 복잡성 제거.  
* <b>보안 및 인증 일원화</b>: 각 서비스별로 반복 구현하던 인증/인가, SSL 핑거프린팅을 게이트웨이 단으로 집약.  
* <b>클라이언트 커플링 완화</b>: 백엔드 내부 서비스의 변경(IP, 포트, 파티셔닝)이 클라이언트에 미치는 파급 효과 차단.

### 나. 주요 기능

* <b>Routing & Load Balancing</b>: 클라이언트의 URI, Header 기준 요청 분기 및 내부 서비스 인스턴스 간 부하 분산.  
* <b>Authentication & Authorization</b>: JWT 검증, OAuth2 인증 연동, API Key 기반 접근 통제.  
* <b>Traffic Control</b>: Rate Limiting 및 Throttling을 통한 과도한 API 호출 제한 및 서비스 보호.  
* <b>Resilience (Circuit Breaker)</b>: 백엔드 서비스 장애 시 빠른 실패(Fail-fast) 및 Fallback 응답을 반환하여 장애 전파 방지.  
* <b>Protocol Translation</b>: 클라이언트의 HTTP/REST 요청을 내부 gRPC, AMQP, SOAP 등으로 프로토콜 변환.

### 다. 적용 시 고려사항 및 적용 사례

* <b>적용 시 고려사항</b>:  
* <b>Single Point of Failure (SPOF)</b>: API Gateway 장애 시 전체 시스템 마비 위험이 존재하므로 로드밸런서 하단에 다중화(HA) 구성 필수.  
* <b>Latency Overhead</b>: 모든 트래픽이 게이트웨이를 거치므로 네트워크 홉 추가에 따른 레이턴시 최적화(비동기 I/O 적용) 필요.  
* <b>복잡도 증가</b>: 라우팅 규칙 및 인증 필터 정책이 집중되므로 게이트웨이 자체의 유지보수 체계 수립 필요.

* <b>적용 사례</b>:  
* <b>금융권 Open API 플랫폼</b>: 외부 핀테크 기업에 금융 데이터를 안전하게 제공하기 위해 API Gateway 기반 인증/인프라 제어 구축.  
* <b>E-Commerce MSA 시스템</b>: 주문, 결제, 상품, 배송 등 서비스 분화 환경에서 모바일/Web 앱 관문을 Kong, Spring Cloud Gateway로 일원화.

## 4. 정량적 위험분석 및 4가지 기법

### 가. 정량적 위험분석의 정의 및 필요성

* <b>정정의</b>: 프로젝트 및 정보시스템의 식별된 위험(Risk)이 전체 목표(비용, 일정, 범위)에 미치는 영향을 수치적, 금전적 가치로 정량화하여 산출하는 프로세스이다.  
* <b>필요성</b>: 정성적 위험분석의 주관적 한계를 극복하고, 객관적인 손실 예상액(ALE)을 계산하여 예비비(Contingency Reserve) 산정 및 위험 대응 투자 대비 효과(ROI)를 정밀하게 검증하기 위함이다.

### 나. 4가지 위험분석 기법 및 예시

<b>1) 의사결정나무 분석 (Decision Tree Analysis)</b>

* <b>설명</b>: 불확실한 미래 상황에 대한 여러 선택지와 각 선택지별 발생 확률, 금전적 결과를 나뭇가지 구조로 시각화하여 최선의 의사결정 경로를 선택하는 기법이다.  
* <b>예시</b>: 신규 전산망을 구축할 때 '자체 개발'과 '외주 패키지 도입' 중 선택하는 상황. 자체 개발 시 성공 확률 $70\%$($+10$억 원), 실패 확률 $30\%$($-5$억 원)일 때의 가지별 손익을 계산하여 최적안을 도출함.

<b>2) 금전적 기대값 분석 (EMV: Expected Monetary Value Analysis)</b>

* <b>설명</b>: 미래에 발생 가능한 각 시나리오의 확률($P$)과 그로 인한 금전적 영향($I$)을 곱한 값들의 총합을 계산하는 정량 기법이다.

$$EMV = \sum_{i=1}^{n} (P_i \times I_i)$$

* <b>예시</b>: 데이터 센터 장애 위험 분석 시, 디스크 장애 발생 확률이 $10%$이고 손실액이 $5,000$만 원일 때, 해당 위험의 $EMV = 0.1 \times (-5,000\text{만 원}) = -500\text{만 원}$으로 위험 비용을 수치화함.

<b>3) 몬테카를로 시뮬레이션 (Monte Carlo Simulation)</b>

* <b>설명</b>: 프로젝트 불확실성 요인에 대한 확률 분포를 정의한 후, 무작위 난수를 대량(예: $10,000$회 이상)으로 생성하여 전체 결과의 확률적 분포 모델을 도출하는 기법이다.  
* <b>예시</b>: 개발 일정 지연 위험을 분석하기 위해 각 작업의 소요 기간을 삼각분포(최상, 최악, 최적)로 설정하고 $10,000$번 시뮬레이션하여 "프로젝트가 12월 31일까지 완료될 확률은 $85\%$"라는 신뢰도 기반 준공일을 산출함.

<b>4) 민감도 분석 (Sensitivity Analysis)</b>

* <b>설명</b>: 다른 모든 불확실한 요소들을 고정한 상태에서 특정 위험 변수 하나를 변화시켰을 때 전체 목표에 미치는 영향도를 측정하는 분석 기법이다 (Tornado Diagram 활용).  
* <b>예시</b>: 차세대 시스템 구축 비용 분석 시 '개발자 인건비', '하드웨어 구매비', '환율' 변수를 각각 $10\%$ 변동시켜 검증한 결과, '인건비' 변수가 전체 예산 변동성의 $60%$를 차지하여 가장 민감한 위험 요인임을 식별함.

## 5. 캐시 일관성 (Cache Coherence)

### 가. 캐시 일관성이 필요한 환경 및 이유

* <b>필요 환경</b>: 멀티코어(Multi-Core) 및 멀티프로세서(Multi-Processor) 시스템 환경에서 각 코어가 독자적인 전용 캐시 메모리(L1/L2 Cache)를 보유하고, 하나의 공유 메모리(Main Memory)를 바라보는 다중 처리 아키텍처.  
* <b>필요 이유</b>:  
* <b>데이터 불일치(Inconsistency) 방지</b>: 코어 A가 캐시의 데이터 $X$를 변경($X=10 \rightarrow 20$)한 후 주기억장치에 쓰기 전, 코어 B가 캐시의 old 데이터 $X(=10)$를 읽거나 수정할 경우 연산 오류가 발생함.  
* <b>데이터 상호 연산의 정합성 보장</b>: 동일한 메모리 주소에 대해 모든 프로세서가 항상 가장 최근에 업데이트된 작성 값을 읽을 수 있도록 메모리 일관성을 보장해야 함.

### 나. 디렉토리 프로토콜과 스누피 프로토콜 비교

| 구분 | 스누피 프로토콜 (Snoopy Protocol) | 디렉토리 프로토콜 (Directory Protocol) |
| --- | --- | --- |
| <b>작동 원리</b> | 프로세서들이 공유 버스(Shared Bus)를 지속적으로 감시(Snooping)하여 다른 캐시의 쓰기 동작을 방송(Broadcast) 받아 처리 | 메모리 블록의 공유 상태 및 소유 프로세서 위치 정보를 중앙 디렉토리(Directory)에서 구조체로 관리 |
| <b>통신 방식</b> | <b>Broadcast</b> 방식 (버스 기반) | <b>Unicast / Multicast</b> 방식 (점대점 인터커넥트) |
| <b>확장성 (Scalability)</b> | <b>낮음</b> (코어 수 증가 시 버스 트래픽 병목 발생) | <b>높음</b> (대규모 프로세서 및 NUMA 환경에 적합) |
| <b>하드웨어 구현</b> | 상대적으로 간단함 (버스 감시 회로 구현) | 복잡함 (디렉토리 컨트롤러 및 구조체 메모리 필요) |
| <b>주요 구현 메커니즘</b> | <b>Write-Invalidate</b> / <b>Write-Update</b> (MESI, MOESI 프로토콜 활용) | <b>Directory Controller</b>가 읽기/쓰기 요청을 수신하고 관련 노드에 구속 신호 전송 |
| <b>적합한 시스템</b> | 소규모 멀티코어, 대칭형 다중 처리기 (SMP) | 대규모 분산 공유 메모리, NUMA 시스템 |

## 6. XP (eXtreme Programming)

### 가. XP의 특징 및 5가지 핵심 가치

* <b>특징</b>: 고객 참여, 짧은 반복 개발 주기(Iteration), 변화에 대한 유연한 수용, 단순한 설계 및 고품질 코드 구현을 최우선으로 하는 애자일(Agile) 소프트웨어 개발 방법론이다.  
* <b>5가지 핵심 가치</b>:  
1. <b>의사소통 (Communication)</b>: 개발자, 고객, 관리자 간의 구두 소통 및 시각적 일상의 다이렉트 소통 강조.  
2. <b>단순성 (Simplicity)</b>: 현재 요구사항에 꼭 필요한 최선의 단순한 기능 및 코드만을 구현 (YAGNI 지향).  
3. <b>피드백 (Feedback)</b>: 지속적인 테스트 및 짧은 단위의 릴리스를 통해 고객과 시스템으로부터 신속한 피드백 수렴.  
4. <b>용기 (Courage)</b>: 코드 리팩토링, 테스트 코드 작성, 기존 코드의 과감한 수정에 대한 자신감.  
5. <b>존중 (Respect)</b>: 팀원 상호 간의 역량 존중 및 제품 품질에 대한 다 함께 책임을 지는 문화.

### 나. XP의 주요 실천 방법 (Practices)

<b>1) 개발자 관점 (개발 및 코드 중심)</b>

* <b>Test-Driven Development (TDD)</b>: 실제 코드를 작성하기 전에 실패하는 단위 테스트 케이스를 먼저 작성하고, 이를 통과하는 최소한의 코드를 구현한 뒤 리팩토링하는 기법.  
* <b>Pair Programming (짝 프로그래밍)</b>: 2인의 개발자가 하나의 키보드/모니터 앞에서 한 명(Driver)은 코드를 작성하고, 다른 한 명(Navigator)은 검토/전략을 제시하며 개발.  
* <b>Refactoring (리팩토링)</b>: 소프트웨어의 외부 동작 기능은 유지하면서 내부 코드 구조를 더 가독성 높고 유지보수가 용이하도록 단순화 및 개선.  
* <b>Continuous Integration (CI)</b>: 하루에 수차례 이상 작성한 코드를 중앙 저장소에 통합하여 자동화된 빌드 및 테스트를 수행.  
* <b>Collective Code Ownership (공동 코드 소유)</b>: 시스템 내의 모든 코드는 특정 개인의 소유가 아니며, 팀 내 누구나 필요시 수정 가능.  
* <b>Simple Design (단순 설계)</b>: 현재 발생한 요구사항만 충족시키는 가장 단순하고 명확한 디자인 유지.

<b>2) 관리 및 관리자 관점 (프로세스 중심)</b>

* <b>Planning Game (계획 게임)</b>: 고객이 요구사항(User Story)을 작성하고, 개발자가 추정치를 제시하여 소요 기간과 우선순위를 협의하는 인터랙티브 계획 수립.  
* <b>Small Releases (작은 릴리스)</b>: 실행 가능한 소규모 기능을 자주 릴리스하여 고객에게 신속한 가치 제공 및 피드백 수렴.  
* <b>On-site Customer (상주 고객)</b>: 고객 대표가 개발팀 현장에 상주하여 요구사항 명확화 및 질문에 즉각 답할 수 있는 환경 구성.  
* <b>Sustainable Pace (40-Hour Week)</b>: 오버타임 업무를 지양하여 개발자의 피로도를 낮추고 장기적인 고품질 개발 생산성 유지.  
* <b>Metaphor (메타포)</b>: 전체 시스템 구성을 팀원 및 이해관계자가 쉽게 이해할 수 있도록 직관적이고 공통적인 비유적 언어로 표현.  
* <b>Coding Standards (코드 표준)</b>: 팀 내 모든 개발자가 일관된스타일로 작성하도록 제정된 공통 코드 작성 규칙 적용.

```
1. 개요

  2.1 하드웨어 및 인프라 스펙 (Web/WAS/DB 서버 CPU, Memory, Disk, Network)
  2.2 소프트웨어 아키텍처 및 설정값 (JVM Heap Size, DB Connection Pool, Thread Pool)

  3.2 목표 성능 지표 (Target SLAs)

      - Response Time (응답시간): 평균 및 95 백분위수(95th Percentile) 응답속도 기준

4. 성능시험 수행 결과
  4.1 부하 테스트 (Load Test): 정상 및 최대 예상 부하 시 목표 TPS/응답시간 달성 여부
  4.2 임계 테스트 (Stress Test): 목표 이상의 과부하 부여 시 시스템 붕괴 시점 및 복구 능력 평가
  4.3 내구성 테스트 (Soak Test): 장시간(12~24시간) 연속 가동 시 메모리 누수(Memory Leak) 여부

  5.1 병목 요인 분석 (DB Lock, Slow Query, Connection Pool 부족, JVM GC 지연 등)
  5.2 성능 튜닝 조치 내용 (SQL 인덱스 생성, APM 기반 소스 코드 개선, WAS 파라미터 최적화)
  5.3 튜닝 전/후 성능 비교 (TPS 향상률 및 응답시간 단축 수치 제시)

6. 종합 결론 및 운영 제언
  6.1 성능 목표 달성 여부 최종 판정 (PASS / FAIL)
  6.2 오픈 후 운영 시 주의사항 (피크 타임 모니터링 가이드, H/W 증설 제안)
```

## 8. DMA (Direct Memory Access)

### 가. DMA를 사용하는 이유

* <b>CPU 오버헤드 최소화</b>: 입출력(I/O) 장치와 주기억장치 간 데이터 전송을 CPU의 관여 없이 직접 수행함으로써 CPU가 전송 루프 연산에 낭비되는 것을 방지한다.  
* <b>시스템 처리량(Throughput) 극대화</b>: 대용량 블록 데이터 전송 시 CPU는 다른 고성능 연산 작업을 병렬로 수행할 수 있어 전체적인 시스템 성능과 응답속도가 대폭 향상된다.

### 나. 입출력장치에서 주기억장치로 정보 전송 시 DMA 제어 메커니즘

```
[I/O Device] ---> (1) DREQ ---> [DMA Controller] ---> (2) HRQ  ---> [CPU]
             <--- (4) DACK <---               <--- (3) HLDA <---
                                      |
                                      +===> (5) Direct Data Transfer ===> [Main Memory]
                                      |
                                      +---> (6) Interrupt Signal    ---> [CPU]

```

1. <b>전송 준비 요청 (DREQ)</b>: 입출력장치가 DMA Controller(DMAC)에 데이터 전송 준비 완료 신호(DMA Request)를 전달한다.  
2. <b>버스 제어권 요청 (HRQ)</b>: DMAC는 CPU에게 버스 제어권을 넘겨줄 것을 요청하는 버스 홀드 신호(Hold Request)를 송신한다.  
3. <b>버스 제어권 승인 (HLDA)</b>: CPU는 현재 버스 사이클을 완료한 후, 버스 제어 권한을 승인하는 신호(Hold Acknowledge)를 DMAC에 반환하고 버스를 고임피던스 상태로 전환한다.  
4. <b>전송 승인 응답 (DACK)</b>: DMAC가 입출력장치에 전송 개시를 알리는 DACK(DMA Acknowledge) 신호를 보낸다.  
5. <b>직접 데이터 전송 (Direct Transfer)</b>: CPU를 거치지 않고 DMAC의 주소 및 카운트 버스 제어하에 I/O 장치에서 주기억장치로 데이터 블록을 직접 전송한다.  
6. <b>인터럽트 발생 및 버스 반환</b>: 설정된 전송 카운터가 0이 되어 블록 전송이 완료되면 DMAC는 CPU에 완료 인터럽트(Interrupt)를 발생시키고 버스 제어권을 반환한다.

### 다. DMA 데이터 전송 모드 3가지

* <b>Burst Mode (블록 전송 모드)</b>  
* <b>방식</b>: DMAC가 버스 제어권을 한 번 획득하면 전체 데이터 블록의 전송이 완전히 끝날 때까지 버스를 독점하여 연속 전송하는 방식이다.  
* <b>특징</b>: 데이터 전송 속도가 가장 빠르나, 전송이 완료될 때까지 CPU가 버스를 사용할 수 없어 긴 대기 시간이 발생한다. High-speed 저장장치(NVMe, SSD)에 적합하다.

* <b>Cycle Stealing Mode (사이클 스틸링 모드)</b>  
* <b>방식</b>: CPU가 명령어 실행 중 버스를 사용하지 않는 비활성 주기를 이용하거나, 1개 데이터 워드(Word)를 전송할 때마다 일시적으로 버스 제어권을 한 주기 빼앗아 전송하는 방식이다.  
* <b>특징</b>: CPU 작업과 I/O 전송이 인터리빙되어 CPU의 제어권 점유 영향을 최소화한다. CPU와 I/O 장치가 버스를 동적으로 공유한다.

* <b>Demand Transfer Mode (요구 전송 모드)</b>  
* <b>방식</b>: 입출력장치가 데이터를 준비하여 DMAC에 전송 요청 신호(Demand Signal)를 유지하는 동안에만 데이터 전송을 지속하고, 장치 사정으로 신호가 멈추면 버스 제어권을 즉시 CPU에 반환하는 방식이다.  
* <b>특징</b>: I/O 장치의 데이터 준비 속도가 불규칙하거나 느린 환경에서 효율적이며, 장치 버퍼 상태에 가변적으로 대응한다.
